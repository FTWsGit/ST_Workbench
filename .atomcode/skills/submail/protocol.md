## 🛠️ 四个主命令，走遍天下

只用这些命令跟搭档交流。
统一入口：**优先用裸 `submail`**（主控已装好 PATH）；若你的环境里 `submail` 不可用，退回用派发 prompt 里给的那个完整路径（`bash <SKILL_SCRIPTS>/submail <子命令> ...` 或 `python <SKILL_SCRIPTS>/../src/cli.py <子命令> ...`），前后一致即可。

> 想用裸 `submail` 命令：`source <SKILL_SCRIPTS>/env.sh` 临时生效。

**记住三个身份类参数，含义永远不变，跟哪个命令搭配都一样：**

| 参数 | 含义 |
|---|---|
| `--me`（或 `-m`） | 我是谁（自己的信箱 id） |
| `--to`（或 `-t`） | 发给谁（收件人） |
| `--from`（或 `-f`） | 信是谁发的（用来核对/过滤来信，**不是**"我"） |

核心是 **send / poll / history / status** 四个动词，另有 `hello` 一个别名：

```bash
# 💌 发信 —— 发给单个搭档，发完就走（1 个 round；失败自动重试一次）
submail send --me w1 --to w2 --body "嗨 w2！我这边 A 部分搞定啦，交接给你：……"

# ❓ 发信 + 顺带等答复 —— 加个 --wait，一步到位，不用再单独 poll
submail send --me w1 --to w2 --body "你那边 B 部分完成了吗？给我个type" --wait 90

# 📣 群发 —— 一次告诉所有搭档（不用填 --to，发给当前全部已知信箱，排除自己；不能跟 --wait 同用）
submail send --me w1 --broadcast --body "A 部分完成，交接说明见下！"

# 📬 收一封 —— 谁的信都算，最多等 wait 秒
submail poll --me w1 --wait 60

# 🎯 只等某人的信 —— 旁人的信自动跳过继续等，直到等到或超时（跟上面 send --wait 是同一套逻辑）
submail poll --me w1 --from w2 --wait 90

# 📥 收全部 —— 一次取走信箱里当前所有来信（攒了几封一起读）
submail poll --me w1 --all

# 📊 复盘 / 状态 —— 看聊天记录、看信箱深度
submail history --me w1 --limit 20
submail status --me w1
```

**别名：** `hello`（= 自检 + 群发问候，`--to` 可省略则问候全部）。

**等对方回复，两条路都对，选你顺手的那条：**
- `send --to w2 --wait 90`：一次调用搞定，发信 + 等回复。
- `send --to w2` 然后 `poll --from w2 --wait 90`：分两次调用也完全没问题，只要 `poll` 记得带上 `--from w2`。**如果 `poll` 不带 `--from`，你可能会先读到别人的信，把该等的回复当成"没来"而漏掉。**

短别名：`-m`=`--me` `-t`=`--to` `-f`=`--from` `-b`=`--body` `-w`=`--wait` `-a`=`--all`

**结果怎么看？**

| 命令 | 返回 | 含义 |
|---|---|---|
| `send --to w2` | `sent seq=3 to=w2` | ✅ 送达成功（`seq` 是信件编号） |
| `send --broadcast` | `broadcast sent=2 seqs=[seq=3, seq=4]` | ✅ 群发送达（发给当前全部已知信箱） |
| `send ...` | `error: ...` | ❌ 重试一次仍失败，把 body 改短点再试，还不行就放弃并在结果里说明 |
| `send --wait` / `poll --from` | `msg from=w2 seq=5` + 换行 + 正文 | ✅ 等到回复了，**正文要用起来** |
| `send --wait` / `poll --from` | `no-reply from=w2 after=90s` | ⏳ 等到超时，队友还没空回。**不是错误**，按兜底规则处理 |
| `poll`（不带 `--from`） | `msg from=w2 seq=3` + 换行 + 正文 | ✅ 收到（谁的都算），**正文要用起来** |
| `poll`（不带 `--from`） | `timeout no-message-after=60s` | ⏳ 这段时间没人来信，**不是错误**，别慌，正常继续干活 |
| `poll --all` | `drained 2` + 每封 `[seq=N from=X] body` | 📥 一次取走全部来信；`drained 0` 表示信箱是空的 |
| `history` | `[seq=3 from=w2] <摘要>` | 📊 聊天记录，新的在前 |
| `status` | JSON | 📊 信箱里有几封信、谁最后来过 |

## 🧭 该用哪种命令？—— 3 秒决策表

**核心就一句：按"你要不要对方回复"来选。**

| 你的目的 | 用哪个 | 为什么 |
|---|---|---|
| 我**告知**对方（交接完成、随口闲聊），**不需要他回** | **`send --to w2`** | 发完就走，不占轮次 |
| 要**同时通知多个搭档**（上线、完工、全员公告） | **`send --broadcast`** | 不用填 --to，自动发给全部已知信箱 |
| 我**需要对方的内容/确认**才能继续（等引言、等全文、问进度） | **`send --to w2 --wait 90`** 或 **`send` 完再 `poll --from w2`** | 两条路都是一次调用/两次调用发信+等到对方回信；哪条顺手用哪条 |
| 攒了几封信想一次性读完 | **`poll --all`** | 一次取走全部，比连 poll 好几轮省事 |
| 开工自检 / 收尾复盘 | **`status`** / **`history`** | 看信箱状态 / 回看聊天记录 |

**判断口诀：**
1. 消息发出去**不需要对方回** → `send`
2. 发出去**就是要等对方回** → 在 `send` 上加 `--wait <秒>`，或者发完之后 `poll --from <对方> --wait <秒>`——两个都行，**唯一不能做的是裸 `poll`（不带 --from）去等一个具体的人**，那样先来的旁人消息会把你的等待"打断"，白白浪费一轮。
3. 要**通知所有人** → `send --broadcast`（别挨个 send）
4. 拿不准 → 问自己：我接下来要不要用他的回答？要 → 加 `--wait` 或用 `--from` 过滤；不要 → 裸 `send`/`poll`

**反面教材（上一批新人的血泪）：** 只会用 `send` 发"我写完了"，对方收不到提醒、也不知道该不该回你，交接就卡住了。正确的做法是：交接正文用 `send` 发给对方；需要对方确认收到/继续接力时，`send ... --wait 90` 追问一句"你收到了吗？可以继续吗？" 或者 `poll --from <对方>`。

## 🤝 团队相处之道

1. **开工先问好**：上线就 `hello` 或 `send` 一条问候给搭档，比如"嘿 w1，我是 w2，随时找我！"。气氛对了，合作才顺。
2. **收到信要回应**：搭档给你递了活或者问了问题，处理完记得回个话确认，别让人干等。
3. **多用第一人称**：消息里用"我""你""我们"，像同事聊天，别写机器人式的干巴巴 JSON 感。
4. **说话带上下文**：传递交接内容时，说明白"我做了什么 / 你需要做什么 / 有什么坑"。别只甩一句话。
5. **带点人味儿**：一句"谢谢""辛苦啦""干得漂亮"不花钱，但能让搭档更愿意配合你。

---

## 📋 调度纪律

1. **先干自己的活，再等别人的信**：优先做不依赖他人的部分，最后才 `poll` 依赖项——等待的时候不空烧轮次。
2. **依赖最多等 3 次**：每个依赖项最多等 3 次（`send --wait 60` 或 `poll --from ... --wait 60`）；仍无回信就**自己兜底处理**，并在最终结果里标注：`PENDING: <对方代号> 未回复，已兜底处理`。
3. **收到的信必须用起来**：`send --wait`/`poll` 拿到正文就影响你的下一步动作，不要读完假装没看见。
4. **最终结果要交代清楚**：收尾时写明——收到过谁的信（`seq` 列表）、没等到谁的。可以用 `history` 复盘确认。

## 🆘 死锁兜底（别钻牛角尖）

如果你在等一个永远不会回信的人——**宁可兜底，不要死等**。主 agent 看到你的 `PENDING` 标记后，会重新派一个补漏的 worker 来填坑。所以：

> 等不到？那就自己上！把缺口写清楚，剩下的交给主 agent。我们永远有后手。💪
